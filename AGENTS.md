# Общие правила

1. Не менять структуру сайта, URL, меню, шапку, футер и существующую архитектуру без прямого указания пользователя.

2. Перед значительными изменениями сначала изучать текущую реализацию соответствующей страницы и связанные CSS/JS.

3. Все внутренние ссылки для GitHub Pages должны учитывать базовый путь:
   /bystrotruby-site/

4. Не создавать новые страницы, если пользователь явно этого не попросил.

5. Не удалять существующие страницы, если пользователь явно этого не попросил.

6. Не менять SEO-структуру самовольно.

7. Не придумывать технические характеристики продукции. Если данных нет — оставлять нейтральный текст или запрашивать данные.

8. Это промышленный B2B-сайт. При работе с контентом приоритет:
   - коммерческий интент;
   - техническая точность;
   - понятность для инженеров, снабжения и технических специалистов;
   - SEO без переспама.

9. Изображения технической продукции не обрезать, если это мешает показать изделие полностью.
   Для предметных изображений по умолчанию использовать object-fit: contain.
   Для сюжетных изображений объектов допускается object-fit: cover.

10. Сохранять текущую визуальную систему сайта:
   - белый фон;
   - темно-синий основной цвет;
   - голубые акценты;
   - чистая промышленная верстка;
   - минимальное количество декоративных эффектов.

11. Не добавлять тени, градиенты, карточки и декоративные элементы без необходимости.

11.1. Не подменять отсутствующее изображение фотографией другого товара или другой конструкции. Подпись и alt должны точно соответствовать изображенному изделию. Если подходящего файла нет, использовать нейтральный placeholder с уникальным ID и внести его в единый `content/applications-images-plan.md`.

12. После каждой законченной задачи:
   - проверить git status;
   - выполнить git add .;
   - сделать осмысленный git commit;
   - выполнить git push;
   - сообщить, какие файлы изменены;
   - дать ссылку GitHub Pages для визуальной проверки.

13. Если задача потенциально затрагивает много страниц, сначала проверить масштаб изменений и не переписывать весь сайт без необходимости.

14. Перед массовой заменой ссылок или контента сделать поиск по проекту и убедиться, что замена не затронет нерелевантные места.

15. Не использовать серверные технологии, фреймворки или сборщики без прямого указания. Проект сейчас статический HTML/CSS/JS.

## Content writing

Перед созданием или редактированием любого пользовательского контента сайта обязательно прочитать `CONTENT-GUIDE.md`.

`CONTENT-GUIDE.md` является обязательной редакционной политикой проекта.

Исследование предметной области и техническая корректность имеют приоритет над объемом текста и рекламным стилем.

После написания или существенного изменения страницы обязательно выполнить отдельный редакторский проход по правилам `CONTENT-GUIDE.md`.

Не публиковать новую коммерческую/SEO-страницу до выполнения этой проверки.

## Catalog architecture

Перед созданием или изменением:

- меню;
- структуры каталога;
- категорий;
- подкатегорий;
- фильтров;
- SEO-посадочных страниц;
- товарной классификации

обязательно прочитать `CATALOG-GUIDE.md`.

Не создавать промышленную классификацию только на основании внутренних знаний модели.

Если добавляется новая предметная область, сначала провести исследование профессиональной классификации и только затем предлагать структуру.

При изменении существующей структуры сначала провести аудит, а затем показать предлагаемую иерархию. Не менять меню до проверки структуры пользователем.
